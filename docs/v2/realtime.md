## 2. 핵심 설계 질문

- [ ] **전송 프로토콜**: WebSocket(Spring STOMP) vs Server-Sent Events vs 외부 Pub-Sub(Ably/Pusher)
- [ ] **메시지 저장 정책**: 라이브 방 종료 후 보관 기간 / 삭제 vs 아카이브
- [ ] **모더레이션**: AI 자동 필터(Django sidecar `#206` 재사용) + 방장/관리자 수동 도구
- [ ] **스케일 설계**: 동시접속 목표 (예: 라이브 1개 10k), 수평 확장 시 브로커 선택 (Redis pub-sub vs Kafka)
- [ ] **멱등성/중복**: 클라이언트 재연결 시 메시지 중복 방지 (clientMessageId 기반)
- [ ] **하트 이벤트**: 개별 이벤트 전송 vs 집계(1초 버킷) — 브로드캐스트 비용 관점
- [ ] **도네이션 오버레이 정책**: 금액별 강조/효과, 필터링(비속어/악성 닉네임)
- [ ] **인앱 알림 수신함**: 저장 TTL, 읽음 처리, 푸시 연동 여부 (Defer된 네이티브 의존)

## 3. 선행 의존성

- **인증**: 채팅 작성자 식별 필요 → 인증(P0/P1) 선행
- **커뮤니티**: 알림은 커뮤니티(P0) 이벤트 기반
- **멤버십 원장**: 도네이션(P1)은 monetization P1 원장 선행
- **AI sidecar**: 채팅/도네이션 실시간 필터

## 4. Discovery Spike

- [ ] WebSocket vs 외부 Pub-Sub 비용/SLA 비교 (동시접속 10k 가정)
- [ ] Redis pub-sub 브로커 운영 복잡도 평가 (이미 캐시로 Redis 사용 여부 확인)
- [ ] 동시접속 부하 테스트 스크립트 설계 (Gatling/Artillery)
- [ ] 도네이션 UI/UX 경쟁 서비스 벤치마크 (위버스/트위치/치지직)
