## 0. 로드맵 원칙

### 범위 정의
- **대상**: MVP(`docs/mvp/**`)에서 제외된 항목 중 **"실제 서비스할 수 있게 메인 기능에 충실한 범위"**
- **MVP → v2 방향 전환**: MVP는 "읽기 소비(뉴스/라이브 시청)" 중심 → v2는 **"팬덤 참여(커뮤니티/실시간/결제)"** 중심
- **제외 기준**: 운영 최적화·관측성·플랫폼 확장만을 위한 항목은 v2에서 빼고 "Defer" 로 분리 (별도 운영 로드맵에서 다룸)

### 우선순위 체계 (MoSCoW 변형)
- **P0 (Must)**: 서비스 런칭 전 반드시 필요 — 없으면 "팬덤 플랫폼"이라 부를 수 없는 기능
- **P1 (Should)**: 시장 경쟁력/수익화 필수 — 없으면 단기 유지는 가능하지만 성장 막힘
- **P2 (Could)**: 있으면 좋은 보조 기능 — P0/P1 안정화 후 착수
- **Defer**: v2 범위 밖 — 별도 로드맵에서 논의 (아래 "Defer 사유" 참조)

## 2. 의존성 그래프

```
[인증 기반]
  이메일 회원가입 (P0) ──┐
                         ├──> [커뮤니티 H003 (P0)] ──┐
  추가 소셜 로그인 (P1) ─┘                           │
                                                     │
                                                     ├──> [투표 H004 (P1)]
                                                     │
                                                     ├──> [고객센터 H023 (P1)]
                                                     │    (신고/모더레이션 플로우 공유)
                                                     │
                                                     └──> [실시간 인터랙션 채팅 (P0)]
                                                              │
                                                              │  (WebSocket 인프라 공유)
                                                              ▼
                                                          [하트/도네이션 (P1)]
                                                              ▲
                                                              │
[결제/원장 기반]                                              │
  멤버십 H009 (P1) ──> PG 연동 · 포인트 원장 ──────────────────┤
                           │                                  │
                           └──> [광고 & 리워드 H008 (P2)]      │
                                                              │
                                                              │
[콘텐츠 파이프라인 확장]                                       │
  차트 크롤러 (P0) ──> 콘서트 크롤러 (P1)                     │
         │                   │                                │
         │                   └──> (티켓 연동 검토)            │
         │                                                    │
         └──> YouTube Data API 보강 (P2)                      │
                                                              │
[AI / 관측성]                                                 │
  고도화 요약 (P2) ← Django AI sidecar 확장                   │
  Grafana alerting (P2) ← MVP Micrometer metrics              │
```

**의존성 해석 포인트**
- **인증이 모든 쓰기의 뿌리**: P0 커뮤니티 착수 전 이메일 회원가입 or 최소 1개 소셜 확정 필요 (Google만으로는 한국 시장 이탈 리스크).
- **WebSocket은 채팅·하트·도네이션의 공통 기반**: 채팅(P0) 설계 시 하트/도네이션(P1) 확장 포인트까지 같이 그려야 재작업 방지.
- **멤버십 원장이 수익화의 허브**: 멤버십(P1) → 하트/도네이션(P1) → 광고&리워드(P2) 가 모두 동일 원장을 쓴다고 가정. 멤버십 스키마 설계 시 포인트/리워드 확장 고려.
- **차트 → 콘서트 크롤러**: 데이터 소스 성격이 유사해 파이프라인 재사용 가능. 차트를 먼저 하며 공통 모듈을 뽑으면 콘서트 착수 속도 빨라짐.

## 3. 마일스톤 제안 (Draft)

> **주의**: 아래 일정은 **의존성 기반 순서 제안**일 뿐, 실제 출시 시점은 MVP 실데이터(WAU, 이탈 지점, 피드백) 보고 재조정.

### v2.0 — "참여 가능한 팬덤 플랫폼"
**목표**: 팬이 **가입하고 글 쓰고 대화할 수 있는** 최소 기능
- P0 전체:
  - 이메일 회원가입
  - 커뮤니티 (H003) — 게시글/댓글/좋아요/신고 기본
  - 실시간 채팅 (기본 — 방/메시지/간단 모더레이션)
  - 차트 크롤러
- P1 일부 (시장 필수):
  - 추가 소셜 로그인 (Kakao 먼저, 국내 유입 우선)

### v2.1 — "수익화 + 상호작용 심화"
**목표**: 팬이 **아이돌에게 기여**(투표/도네이션/멤버십)할 수 있는 기능
- P1 나머지:
  - 투표 (H004)
  - 멤버십 (H009) — PG 연동
  - 하트/도네이션 — 멤버십 원장 재사용
  - 콘서트 크롤러
  - 고객센터 (H023)
- P1 추가 소셜 로그인 확장 (Naver/Apple)

### v2.2 — "운영 안정화 + 광고 모델"
**목표**: 데이터/운영 안정성 + 광고 수익 다각화
- P2:
  - 광고 & 리워드 (H008) — 멤버십 원장 위에서 리워드 포인트
  - Grafana 대시보드 + 기본 Alerting
  - YouTube Data API 메타데이터 보강
  - 고도화 요약/감성 분석
